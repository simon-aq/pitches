Putting a web platform on top of legacy tools, without rewriting them

A US veterinary diagnostic imaging group ran billing and its radiology workflow on dozens of old Python command-line tools. I built web apps on top of those tools instead of replacing them. Work that used to wait for the one person with server access moved to screens the billing and operations teams use themselves.

01 · The starting point

Dozens of tools that worked, and few people who could use them

Not one program, dozens

Billing and the radiology workflow ran on Python tools older than the team's version control. Their author dates some of them back about 15 years: 146 scripts with their own entry point, Windows launchers, shell pipelines.

Mistakes surfaced at month-end

Most configuration errors only showed up when the monthly billing report was produced. The team's own advice was to run it a few days early and look for lines priced at zero.

A 12-option menu for prices

Prices were edited through a console menu, with no preview of what a change would affect. In practice, the billing team filled in a spreadsheet and sent it to the one person who could apply it on the server.

Two rules from day one

Operations could not stop, and logic that worked could not be rewritten in one go. The old tools and anything new had to run side by side and agree on every bill.

02 · The decision

Wrap the old tools instead of replacing them

Leave them running

The legacy tools stayed where they were, reading and writing the same databases. Nothing the business relied on was switched off.

Give them a machine interface

JSON output, flags that turn off emails and uploads, and tagged releases. Now a program can call a tool safely, not only a person at a console.

Build the apps on top

The billing app runs six of the tools as pinned bundles, through one entry point that forces read-only database sessions. The operations console depends on seven legacy packages, pinned the same way.

Plug into what already exists

Company sign-in with roles, the HL7 engine that feeds orders and reports, and the shared databases. Every app runs in Docker behind the corporate VPN.

Simplified. The billing app is called BCT and the operations console Atlas.

03 · Billing configuration (BCT)

The old scripts still compute the bill. The configuration moved to a browser.

The billing team edits it themselves

The tables the legacy billing reads are edited here, by the billing staff, through six roles. Five months after the first write screens went live, 91% of configuration changes came through here (99.7% for prices and pay settings), every one with an author and a written reason. The rest come from legacy automation that still writes mappings by design.

The rules are visible

A row is flat-priced or uses a priority triplet, never both. The database refuses the invalid case, and the screen states the rule before anyone saves.

Every mapping checked as the page opens

Codes missing from the catalog, mismatched modalities and integration channels that no longer exist are counted and flagged in the table.

One queue for every break

Before, these checks only ran inside the monthly script, when a broken exam was already a backlog item. Now they run whenever the page opens. Mid-month, the billing clerk spotted zero-priced lines this way, before the close; the cause was a gap the legacy code had been reading silently.

New clients, checked on the way in

Clients can be created and copied in the app. Onboarding a real client through the import, the billing lead wrote: “BCT reported about 10 other errors almost immediately, which was great.”

The pay run, a button

The monthly pay calculation used to need someone with shell access on the server. It is now a role-gated button with a job queue: status, cancel, inspect.

Fictitious values throughout.

04 · Operations (Atlas)

From a long prior-tracking script to the operations console

Every prior-study request, in one list

Radiologists compare a new study with the patient's earlier ones. Operations used to track those requests with a script of more than 1,500 lines installed on each workstation, under one shared login. Now it is a web page with personal sign-in.

Status at a glance

Waiting, received, pulled manually, dictated without priors: each request carries its state, and the list filters by it.

One request, end to end

Patient, current exam, requested prior and who was notified, read live from five external systems across PostgreSQL and SQL Server.

It grew beyond priors

Reading worklists, a study tracer, report refiles and infrastructure alarms moved into the same console. One question that once took five rounds of hand-written SQL, why a radiologist isn't getting cases, is now a page.

Production screens, masked before capture: patients, MRNs and accession numbers are fictitious.

05 · The second fire (Meridian)

A useful app built with AI, with nobody owning its data

Built fast, outside engineering

A non-engineer built a scheduling and credentialing app with Claude Code. It worked. It also ran on a private SQLite file, refilled from spreadsheets and deployed from one workstation.

It drifted from production

Radiologists were matched by display name against a production roster keyed by username. Privileges were recorded before the production systems agreed. Demand came from imported spreadsheets.

Rebuilt on engineering foundations

A real database keyed to the production identities, a read-only sync from the production roster, company sign-in with roles, hardened containers on the company's existing server, CI and scheduled jobs.

The month at a glance

Shifts per day, days with pending requests, days with coverage gaps.

Coverage, hour by hour

Each day shows who is reading and the hours nobody covers, so a gap is visible before it happens.

Which sites can be read

From who is on the schedule and their privileges: the sites each day's radiologists can read for.

One record per radiologist

One roster shared by every department, kept in line with production by the sync job.

Built to replace the manual steps

Re-importing spreadsheets, re-matching people by name, renewing certificates by hand. The rebuild runs on the company's server with the roster syncing from production, ready to take over from the original app.

Staging with sample data, masked as well.

AI lets non-engineers build fast. Someone still has to own state, data integrity and infrastructure.

06 · Decisions that mattered

Where the reliability comes from

The database is the validator

The rules that must never break live in PostgreSQL constraints. The app turns their errors into plain language and checks the same rules before saving.

An audit trail the database writes

Triggers on seven configuration tables store the old row, the new row, who and why, in a log that refuses edits. When a re-run of a past month gave a different pay total, the log traced the cause to specific configuration changes within minutes.

Read-only by default

Sessions open read-only, CI fails on raw SQL writes, and every call into a legacy tool runs read-only. Writes were switched on one action at a time behind feature flags.

Checking what the AI writes

Claude Code builds from specs I write. Type checks and tests against a real PostgreSQL run in CI, and contract tests fail if new code and the legacy tools drift apart.

07 · How the work ran

A short loop with the people who own each process

I worked with the operations lead and the billing lead, and by email with members of their teams, always with both leads copied. They described a problem, I turned it into a spec, and Claude Code built against it. Each repository carries its conventions, architecture decisions and specs, so the agent starts every task with the context.

  • ~15 hmedian from a billing-app ticket to its fix, merged (nights and weekends included)
  • 43 of 64working days with changes merged, over three months
  • 1 a dayfeedback from the team on the work, about once per working day

I built the billing app and the scheduling rebuild on my own. I started the operations console and built its first version, including the core request flows; a colleague has since taken over most of its development. I estimate this used to take a team of five or six.

08 · What I take from it

Three things I'd do again

Keep what works. Old code that gives the right answer is an asset. Giving it an interface, pinning it and testing the seam was faster and safer than betting the business on a rewrite.

AI makes building cheap, not owning. The scheduling app was useful and quick to build. What it lacked was someone responsible for its data, its state and where it runs.

Put the checks where mistakes are cheap. The database refuses invalid configuration, CI refuses untested code, and the audit trail shows who changed what. That is what lets me build quickly with AI without trusting it blindly.
